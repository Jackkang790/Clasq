# Clasq-FrontEnd 코드 분석

## 분석 범위

- 대상: `Clasq-FrontEnd` 프로젝트의 추적 가능한 소스·설정·정적 리소스
- 제외: `.venv/`, 모든 `__pycache__/`, 생성된 Python 바이트코드
- 방식: 정적 코드 검토. 실제 Ollama 설치·모델 다운로드·파일 이동은 수행하지 않았다.

## 2026-08-20 후속 수정 사항

MP3 처리 검증 후 다음을 구현했다.

- `ClasqCore.process_file_upload()`은 미디어 분석 결과의 `tags`가 비어 있거나 형식이 잘못된 경우, 파일 확장자와 파일명 토큰으로 기본 태그를 생성한다. 예를 들어 `0.mp3`는 `오디오`, `mp3`, `0` 태그로 저장된다.
- 이 폴백은 AI 분석 자체가 실패한 경우에도 적용되므로, DB의 `tags`가 빈 문자열이 되어 정리 목록에서 빠지는 문제를 방지한다.
- DB 저장 결과를 분석 반환값의 `db_save`에 포함했다. `FolderScanAndTagWorker`는 이 값을 확인해 저장 실패 시 성공 완료 신호 대신 파일명과 원인을 포함한 오류 신호를 UI에 보낸다.

이 변경은 "분석 완료" 메시지가 DB 기록 실패를 숨기지 않도록 하며, 실패한 미디어 파일도 파일명 기반으로 검색·정리할 수 있게 한다.

## 한눈에 보는 구조

`Clasq-FrontEnd`는 로컬 파일을 추출·AI 분류·SQLite 저장·자연어 검색·태그별 이동하는 PySide6 데스크톱 앱이다.

```text
main.py
  └─ MainWindow (프레임리스 UI / 페이지 이동)
      ├─ SettingsView ─┐
      ├─ SearchView ───┼─ ClasqCore
      ├─ OrganizeView ─┘    ├─ TextExtractor / FileAnalyzer
      └─ SavedView           ├─ FileRegistryManager (SQLite)
                             ├─ SearchQueryParser (Ollama)
                             └─ SearchEngine

ollama_manager.py: Ollama 설치·실행·모델 준비·HTTP 호출
```

## 실행 흐름

1. `main.py`가 시작될 때 `OllamaManager.initialize()`가 Ollama 설치 여부, 서버, `gemma3` 모델, 모델 응답을 차례로 확인한다.
2. `MainWindow`가 단일 `ClasqCore` 인스턴스를 생성하고 설정·검색·정리 화면에 주입한다.
3. 폴더/파일 태깅은 `FolderScanAndTagWorker` 스레드에서 실행된다.
4. `ClasqCore.process_file_upload()`가 형식별 텍스트/이미지/미디어 처리를 분기하고, Ollama가 생성한 태그·설명을 SQLite `files` 테이블에 저장한다.
5. 검색은 Ollama가 질의를 `@검색` 또는 `@대화` JSON으로 분류하고, `SearchEngine`이 SQL `LIKE` 검색과 AND→OR 폴백을 수행한다.
6. 정리는 첫 번째 태그를 기준으로 폴더를 만들고 실제 파일을 옮긴 뒤 DB 경로를 갱신한다.

## 모듈별 역할

| 영역 | 파일 | 책임 |
| --- | --- | --- |
| 앱 진입점 | `main.py` | 애플리케이션 부팅, 전역 스타일, 창/페이지 내비게이션 |
| AI 런타임 | `ollama_manager.py` | Ollama 실행 파일 검색, 설치 스크립트 실행, 서버·모델 확인, REST 호출 |
| 유스케이스 | `src/utils/core.py` | 업로드/배치 분석, 검색, DB 통계, 태그 그룹화, 파일 이동 조율 |
| 콘텐츠 처리 | `src/utils/file_pipeline.py` | TXT·PDF·Office·HWP 계열 읽기, 이미지 축소, Whisper STT, LLM/Vision 메타데이터 생성 |
| 영속성 | `src/utils/db_manager.py` | DB 초기화·마이그레이션, 해시 중복 감지, 관리 경로, 파일 레코드 저장 |
| 검색 | `src/utils/query_parser.py`, `search_engine.py` | LLM 의도 파싱, 불용어·동의어 기반 SQLite 검색 |
| 비동기 | `src/utils/workers.py` | 폴더/파일 분석 및 질의 처리를 UI 스레드 밖에서 수행 |
| UI | `src/ui/**` | 설정·검색·정리·저장목록과 커스텀 타이틀바/사이드바 |

## 잘 설계된 점

- `ClasqCore`에 업무 흐름을 모아 UI가 세부 처리 구현을 직접 알지 않도록 한 점이 좋다.
- SQLite에 WAL과 `busy_timeout`을 설정하고, 대량 처리 중 연결을 재사용하려는 설계가 있다.
- 파일 해시(SHA-256)로 내용 중복을 감지하며, 중복 파일을 별도 폴더로 이동하는 정책을 제공한다.
- 이미지·미디어·문서의 실패를 폴백 메타데이터로 바꿔 단일 파일 오류가 전체 처리 중단으로 이어지지 않게 했다.
- SQL 값은 바인딩 파라미터로 전달해 일반적인 SQL 삽입 위험을 피한다.
- 긴 AI 처리와 검색을 `QThread`로 분리해 UI가 멈추는 문제를 줄였다.

## 주요 문제와 우선순위

### P0 — 실제 파일 이동과 DB 트랜잭션의 원자성이 보장되지 않음

`ClasqCore.organize_files()`는 파일을 `shutil.move()`로 먼저 이동하고 이후 DB를 갱신한다. DB 업데이트나 최종 `commit()`이 실패하면 DB는 롤백되지만 이미 이동한 파일은 원래 위치로 돌아가지 않는다. 반대로 일부 이동에 성공한 뒤 오류가 난 경우에도 성공 응답을 반환한다.

- 영향: DB 경로와 실제 파일 위치가 달라질 수 있고, 재시도 시 "파일 없음" 오류가 생긴다.
- 권장: 이동 계획과 DB 갱신을 분리하고, 실패 시 역순 보상 이동(rollback)을 수행한다. 운영 기능이라면 작업 전 미리보기·확인·작업 로그·복구 기능을 제공한다.

### P0 — 기본 중복 정책이 사용자의 파일을 예고 없이 이동함

`FileRegistryManager`의 기본 `duplicate_policy`는 `quarantine`이다. 분석/태깅 과정에서 내용이 같은 파일을 감지하면 원본 폴더 아래 `_duplicates`로 물리적으로 옮긴다.

- 영향: "분석" 또는 "스캔"이라고 생각한 사용자가 파일 위치 변경을 경험할 수 있다.
- 권장: 기본값을 `skip` 또는 단순 표시로 바꾸고, 실제 이동은 사용자 확인 후 별도 작업으로 실행한다. 설정 화면에 정책과 대상 경로를 명확히 표시한다.

### P1 — 중복된 메서드 정의가 앞선 구현을 덮어씀

- `src/utils/core.py`에 `scan_directory_files()`가 두 번 정의되어 첫 번째 구현은 실행되지 않는다.
- `src/ui/views/organize_view.py`에 `_start_ai_tagging()`, `_on_tagging_finished()`, `_on_tagging_error()`가 각각 두 번 정의되어 앞선 구현(진행률 연결 포함)이 무효화된다.

영향은 기능 변경 시 어떤 코드가 실제 실행되는지 혼동하고, 첫 번째 구현에 대한 수정이 반영되지 않는 것이다. 중복을 제거하고 단일 구현에 진행률 UI까지 연결해야 한다.

### P1 — 저장목록 화면이 실제 데이터베이스와 연결되지 않음

`SavedView`는 `core`를 받지 않으며 더미 3행을 표시한다. "저장" 동작도 테이블 내용을 `print()`할 뿐 SQLite에 반영하지 않는다.

- 영향: 사용자는 DB에 저장된 태그를 편집·확인한다고 생각하지만 실제로는 아무 변경도 저장되지 않는다.
- 권장: `SavedView(core=self.core)`로 주입하고, DB 조회/태그 수정 API를 구현한다. 더미 데이터와 안내 문구는 제거하거나 개발 모드로 제한한다.

### P1 — 앱 시작이 네트워크 설치와 대형 모델 다운로드에 강하게 결합됨

시작 시 `OllamaManager.initialize()`가 없으면 PowerShell 설치 스크립트를 실행하고, 모델이 없으면 `gemma3`를 내려받은 뒤 추론 테스트까지 한다. 이 모든 작업은 `QApplication` 생성 전 동기 실행된다.

- 영향: 첫 실행에 장시간 멈춰 보이며, 네트워크/권한 실패 시 UI에서 복구나 설정을 할 수 없다.
- 권장: 앱은 먼저 열고, 별도 준비 화면·백그라운드 작업·취소/재시도·오프라인 안내를 제공한다. 자동 설치는 사용자 동의 후에만 실행한다.

### P1 — 모델 설정이 일관되지 않음

진입점은 `gemma3`를 지정하지만 `ClasqCore`, `SearchQueryParser`, `FileAnalyzer`의 기본값은 `gemma2:9b`이고 Vision 모델은 `llava`다. 초기화는 텍스트 모델만 준비한다.

- 영향: 이미지 분석 시 `llava`가 없으면 폴백 처리되고, 다른 실행 경로에서는 서로 다른 텍스트 모델을 요구할 수 있다.
- 권장: 하나의 설정 객체/파일에서 텍스트·비전·Whisper 모델을 정의하고, 필요한 모델을 모두 사전 점검한다.

### P2 — 외부 AI 응답 검증이 부족함

LLM JSON을 파싱한 후 `tags`가 문자열인지, 배열 요소가 문자열인지, 개수/길이가 적절한지 검증하지 않는다. `save_file_result()`는 곧바로 `tags[0]`, `','.join(tags)`를 사용한다.

- 영향: 모델이 규격 밖 JSON을 반환하면 저장 단계가 실패하거나 비정상 태그가 DB에 저장될 수 있다.
- 권장: Pydantic/dataclass 스키마로 결과를 검증·정규화하고, 실패 시 안전한 빈 태그와 오류 원인을 저장한다.

### P2 — 검색 정확도와 자원 관리 보완 필요

- 확장자 필터가 `file_path LIKE '%{ext}'`여서 대소문자·공백 정규화에 약하고, `ext` 값에 `.`가 없는 경우 의도대로 동작하지 않을 수 있다.
- `SearchEngine._execute_sql_query()`는 예외 시 연결을 닫지 못한다. `with sqlite3.connect(...) as conn:` 또는 `try/finally`를 사용해야 한다.
- 모든 검색이 여러 `LIKE '%...%'`를 사용하므로 데이터가 커지면 느려진다.

권장: 확장자를 별도 DB 열에 정규화해 인덱싱하고, SQLite FTS5 또는 전문 검색 도입을 검토한다.

### P2 — 예외 상태를 성공으로 취급하는 경로가 있음

`process_file_upload()`는 텍스트 추출 상태가 오류여도 분석 결과를 저장하려 시도하고, `process_folder_batch()`는 반환된 결과의 `status`와 DB 저장 성공 여부를 확인하지 않고 호출만 성공하면 성공 수를 증가시킨다. `process_media()`도 STT 오류에서 `SUCCESS` 상태를 돌려준다.

- 권장: `SUCCESS`/`FAILED`를 명확히 전파하고, 배치 결과에 분석 실패·저장 실패·건너뜀을 분리 집계한다.

### P2 — UI 완성도 및 유지보수성

- `OrganizeView`가 초기 더미 데이터를 잠시 채운 뒤 DB 데이터로 덮어쓴다.
- 설정 화면은 약 800행으로 UI 구성, 프리셋, DB, 워커 제어 책임이 혼재한다.
- `tempCodeRunnerFile.py`에는 의미 없는 `g`만 남아 있다.
- `TitleBar.set_maximized_icon()`은 최대화 여부와 무관하게 같은 `zoom_in.svg`를 지정한다.

권장: 화면별 모델/서비스를 분리하고, 임시 파일을 삭제하며, 최대화/복원 아이콘을 분리한다.

## 데이터 모델과 파일 처리 주의점

- `files`: 파일명, 경로(UNIQUE), AI 코멘트, 카테고리, SHA-256, 크기, 생성/수정 시각, 태그, 원본 경로를 보관한다.
- `managed_paths`: 사용자가 등록한 관리 경로를 보관한다.
- 자동 정리는 파일의 **첫 번째 태그만** 사용한다. 여러 태그를 붙여도 하나의 분류 폴더에만 들어간다.
- `sync_missing_files()`는 DB에 있으나 디스크에 없는 모든 항목을 삭제한다. 외부 드라이브가 일시적으로 분리된 경우에도 기록이 삭제될 수 있으므로, 즉시 삭제보다 `missing` 상태/유예 기간이 안전하다.
- OCR 라이브러리는 의존성에 있으나 분석 흐름에서 OCR 결과를 채우지 않고 `ocr_text`는 빈 값이다. 이미지 내 텍스트 검색이 요구사항이면 구현이 더 필요하다.

## 의존성 및 배포

- `requirements.txt`에는 `Pyside6`와 `PySide6==6.11.1`처럼 중복·혼합 표기가 있다.
- 개발/실행/선택 기능 의존성이 한 파일에 섞여 있어 설치 비용이 크다. Whisper·EasyOCR·OpenCV·SciPy 등은 선택 기능별 extras 또는 잠금 파일로 분리하는 편이 낫다.
- `.gitignore`는 `.venv`, `__pycache__`, `*.db`를 제외한다. 이미 추적된 DB가 있다면 별도로 Git 추적 해제가 필요하다.

## 권장 정비 순서

1. 중복 메서드와 임시 파일을 제거하고, 실제 DB 저장목록을 연결한다.
2. 파일 이동·중복 격리 앞에 명시적 사용자 확인과 복구 가능한 작업 로그를 도입한다.
3. 모델 설정을 단일화하고, 시작 단계의 자동 설치/다운로드를 비동기 준비 화면으로 옮긴다.
4. AI 출력 스키마 검증과 배치 결과의 실패 집계를 구현한다.
5. 검색용 확장자 정규화·인덱스/FTS를 적용하고 테스트를 추가한다.
6. UI·DB·파일 서비스 단위 테스트와 임시 SQLite DB를 사용하는 통합 테스트를 마련한다.

## 결론

핵심 파이프라인은 이미 갖춰져 있으며, 특히 DB 레지스트리와 비동기 UI 연결의 방향은 적절하다. 다만 이 앱은 실제 사용자 파일을 이동·격리하므로, 데이터 손실·불일치를 막는 원자성/사용자 확인을 최우선으로 보강해야 한다. 그 다음 더미 UI와 중복 코드를 정리하면 기능 신뢰성과 유지보수성이 크게 개선된다.
